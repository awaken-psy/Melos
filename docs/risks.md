# 已知残留风险

Melos 在各维度都实现了对抗策略，但仍有一些无法完全消除的残留风险。

## 风险等级说明

| 等级 | 含义                                           |
| ---- | ---------------------------------------------- |
| 🟡    | 存在理论风险，但在当前对抗场景中不构成实际威胁 |
| 🟢    | 存在潜在风险，已有合理默认策略规避             |
| 🔴    | 严重风险，需要立即处理（当前无此类风险）       |

## 风险列表

### 🟡 服务端轨迹统计分析

**风险描述**：轨迹数据来自同一场地的采集数据，虽然每次运行有速度变化和随机噪声，但整体轨迹形状高度相似。如果检测方收集了足够多的用户轨迹样本，可能通过统计分析方法（如轨迹聚类、形状哈希比较）筛出异常。

**影响程度**：中。需要检测方具备较强的数据分析能力和足够的样本量。

**可能的缓解方向**：
- 引入轨迹变异算法，在基础轨迹上添加随机偏移
- 支持多个场地数据，分散检测风险
- 添加轨迹指纹多样性（不同起跑点、不同内/外道偏移）

### 🟡 磁力计朝向

**风险描述**：微信小程序的地图组件通过 native 层（NDK）直接读取磁力计硬件传感器，绕过了 Java SensorManager 的 hook。因此 Melos 注入的磁力计数据无法到达地图组件，地图上的方向指示锥不受控。

**影响程度**：低。磁力计主要影响地图上的朝向显示，不影响轨迹追踪和距离计算。大多数运动检测系统不以磁力计数据作为核心判据。

**技术原因**：微信使用腾讯地图 SDK，其底层通过 NDK 直接与传感器 HAL 交互，不走 Java SensorManager。要 hook 这一层需要修改 native 库（如 PLT hook），实现复杂度远高于 Java hook。

### 🟢 服务端合理性校验

**风险描述**：服务端可能对上传的运动数据做合理性校验，例如运动时段是否合理（凌晨 3 点跑步？）、距离/时长比是否合理（3 分钟跑完 5 公里？）。

**影响程度**：低。Melos 默认配速约 9km/h（5:30 min/km），属于正常慢跑速度范围，不会触发这种基本合理性检查。运动时段由用户自行决定。

**注意事项**：用户应选择合理的运动时段和配速，避免明显不合理的参数组合。
